# PolyNexus 阶段 9 任务清单

## 0. 当前定位

阶段 9 不再继续回答“core 证据够不够强”这个问题，因为阶段 8 已经把方向收得很清楚：

**PolyNexus 继续走“带 agent 行为的专业分析工作台”，但现在要把阶段 8 的证据、benchmark 和回退语义真正做进主工作台。**

阶段 8 已经把下面这些东西做出来了：

- core evidence pack
- 复合 objective 与回退逻辑
- symptom -> parameter 诊断动作桥
- evidence-driven prompt
- benchmark 准确度统计
- joint consistency 回流

但它们目前还更像“系统已经懂了”，不是“用户已经顺手用了”。

所以阶段 9 要做的是：

**把 PolyNexus 从“证据驱动的受控优化工作台”，推进到“证据可复核、试验可连续、判断更顺手的可信验证工作台”。**

## 1. 阶段目标

阶段 9 只解决一个问题：

把阶段 8 已经建立起来的准确度链路，继续推进到主工作台的日常复核流程里，让用户能更自然地：

1. 看懂当前结果为什么更可信或还不够可信
2. 明确下一轮应该优先修什么问题
3. 让多轮受控尝试保持上下文连续，而不是每次重新开始
4. 在单技术优化和跨技术一致性之间更快来回切换

这一阶段的关键词：

- 证据复核
- benchmark 可见化
- 多轮连续性
- 目标化重试
- joint-aware 审阅
- 可信交付

## 2. 阶段边界

### 2.1 阶段 9 要做什么

- 把阶段 8 的 benchmark / evidence / rollback 语义搬进主工作台 Results 复核流程
- 让受控优化下一轮更像“带目标的验证”，而不是重复按一次按钮
- 让 work memory / history / export 更清楚表达本轮试验链和判断依据
- 让 joint consistency 在工作台里更容易被看见和使用

### 2.2 阶段 9 明确不做什么

- 不做独立聊天式 agent 主界面
- 不做自动无限轮优化器
- 不做全局任务编排平台
- 不把 core 判断权交给 AI
- 不在这一阶段重写主窗口骨架

## 3. 阶段 9 的最小产品模型

阶段 9 的最小模型不是“让系统会说更多”，而是先把这条工作台链路做顺：

1. 用户在 Results 页直接看到结果来源、风险、benchmark 和 joint 冲突线索
2. 用户能判断当前更适合接受、再试一轮，还是去做 joint compare
3. 再试一轮时，系统会明确延续上一轮的目标、剩余风险和关注证据
4. 导出和复盘时，能恢复“为什么接受这次结果”的判断过程

只要这条链顺了，PolyNexus 的 agent 行为就会更像“可信复核助手”，而不是一组分散的调参动作。

## 4. 各任务最小闭环

### P9-T1. Results 证据 / benchmark 复核卡

最小用户故事：

用户在主工作台 Results 页，不用先打开 AI 调参弹窗，也能直接看见这次结果的复核要点：

- 当前结果来源
- benchmark 里 objective delta / accept / rollback / constraint / symptom 的关键信号
- 当前还没消除的风险
- 是否存在 joint consistency 冲突

这一版只做：

- 在现有 Results 视图内增加轻量复核卡，不新建页面
- 优先复用已有：
  - `results_summary`
  - `benchmark_summary`
  - `tuning_context`
  - `joint_ai_context`
- 只表达“当前为什么值得信 / 还不该完全信”

这一版不做：

- 大型 dashboard
- 长篇解释生成
- 全量对比矩阵

验收标准：

- 用户在 Results 页更快理解“这次为什么更准”
- benchmark 不再只存在于弹窗或后台 JSON
- 复核卡不会把现有 Results 区域挤成信息墙

### P9-T2. 受控优化目标化重试

最小用户故事：

用户不是只会重复点一次 Controlled Optimization，而是能明确指定下一轮更想优先处理什么：

- 症状修复
- 约束风险下降
- joint consistency 冲突缓解
- 保守稳定化

这一版只做：

- 在现有受控优化启动前增加轻量目标选择
- 目标只影响已有 prompt / orchestrator 上下文，不开放新参数空间
- 目标文案来自已有 evidence / benchmark / joint context

这一版不做：

- 自由文本规划
- 自动决定所有目标优先级
- 无限轮任务树

验收标准：

- 第二轮比第一轮更像“带明确意图的验证”
- 用户能看懂系统为什么建议这个目标

### P9-T3. 多轮试验链与候选轨迹

最小用户故事：

用户做了不止一轮受控优化后，能看到这几轮其实属于同一条验证链，而不是几份互相独立的报告。

这一版只做：

- 给 controlled optimization run 增加轻量链路表达
- 在 history / work memory / review summary 中表达：
  - baseline
  - accepted / rolled back round
  - 当前最佳候选
  - 当前仍保留的风险

这一版不做：

- 复杂实验项目管理系统
- 全局任务树
- 多用户协同批注

验收标准：

- 多轮尝试的上下文连续性明显增强
- 用户更容易知道“现在这轮是接着哪一轮继续试”

### P9-T4. Joint-aware 复核跳转

最小用户故事：

当单技术结果局部更好，但 joint consistency 仍有冲突时，工作台会更自然地提醒用户切去 joint compare，而不是让冲突留在后台。

这一版只做：

- 在 Results / Work memory / Compare 邻近位置增加 joint-aware 提醒
- 提供一键跳到 `joint.compare`
- 优先暴露：
  - `phi_c` inconsistency
  - `Tm` 双向校验异常
  - `L` 一致性不稳

这一版不做：

- 自动跨技术联合优化
- 联合决策替用户拍板

验收标准：

- 用户更容易看见“单技术更好了，但全局还没统一”
- joint.compare 的入口更像当前任务的自然下一步

### P9-T5. 审阅记忆与导出固化

最小用户故事：

未来回看一个导出包或历史记录时，用户能更快恢复当时的判断依据，而不是只看到最终参数和一个 R2。

这一版只做：

- work memory 增加 benchmark / tuning / joint 的关键摘要
- export manifest / README 增加复核摘要与当前验证链信息
- history 恢复时尽量带回这些摘要

这一版不做：

- 大规模报告模板重做
- 自动生成完整科研结论

验收标准：

- 复盘时更容易回答“为什么当时接受这个结果”
- 导出包更像审阅交付，而不是只是一堆文件

### P9-T6. 阶段回归与边界固化

最小用户故事：

阶段 9 做完后，用户会觉得工作台更像一个可信验证助手，但不会觉得系统开始替自己做科学判断。

这一版只做：

- 为 Results 复核卡、目标化重试、多轮试验链、joint-aware 提醒、导出摘要补定向回归
- 再次固化边界：
  - core 负责证据
  - AI 负责有限建议
  - orchestrator 负责受控试验与回退
  - 用户负责最终判断

这一版不做：

- 大型 E2E 平台
- 主窗口重构
- 无边界 agent 主动规划

验收标准：

- 主链路稳定
- 新能力不制造“AI 比 core 更重要”的错觉

## 5. 推荐顺序

阶段 9 推荐执行顺序：

1. `P9-T1 Results 证据 / benchmark 复核卡`
2. `P9-T2 受控优化目标化重试`
3. `P9-T3 多轮试验链与候选轨迹`
4. `P9-T4 Joint-aware 复核跳转`
5. `P9-T5 审阅记忆与导出固化`
6. `P9-T6 阶段回归与边界固化`

原因：

- T1 先把阶段 8 的准确度信号搬到用户最常看的 Results 页
- T2 再让“再试一轮”真正变成有目标的验证
- T3 把多轮过程串起来，避免上下文碎掉
- T4 把单技术和联合分析之间的切换做顺
- T5 最后把这些判断沉淀到复盘和导出里
- T6 收口补回归，防止阶段越做越散
