# PolyNexus 阶段 6 任务清单

## 0. 当前定位

阶段 6 不把 PolyNexus 直接推成“全自动科研 Agent”，而是把它继续做成：

**带受控 agent 行为的专业分析工作台**

这里的“agent 行为”不是另外套一层聊天壳子，也不是让系统直接替用户下科研结论，而是：

- 先由现有工作台自然积累上下文。
- 再由系统基于这些上下文做可解释、可回退、有限边界内的判断。
- 必要时在既有流程参数里做小范围、多轮、受控的尝试。
- 最后把更可信的候选结果和理由回流到现有工作台里，让用户确认。

也就是你前面明确希望的这条路：

1. 底层仍然是可靠、可复核的分析软件。
2. 上层逐步加入建议、串流程、组织上下文、有限调参的 agent 能力。
3. agent 不急着替用户做最终科研判断，而是帮助用户把结果做得更可信。

## 1. 现有地基

阶段 5 完成后，阶段 6 已经不是从空白开始。

当前主工作台已经具备这些非常适合继续生长的表面：

- `workflow header`
  - 已经能显示当前技术线、当前数据、当前运行状态。
- `Data / Config / Results / Plots / History`
  - 已经形成主要工作流容器。
- `sample browser`
  - 已经能承载样品、batch、回溯和来源上下文。
- `joint hub`
  - 已经是天然的多结果汇聚与判断入口。
- `export bundle`
  - 已经稳定输出 `figures / data / report / metadata`。
- 已有“AI tuning”雏形
  - 当前代码里已经存在多轮 tuning worker、进度反馈、候选配置确认和最佳配置回填。

所以阶段 6 的核心不是“新造一个 agent 页面”，而是：

**让现有工作台先长出足够好的上下文，再把受控 agent 能力嵌入这些现有入口里。**

## 2. 阶段目标

阶段 6 只解决一个问题：

把 PolyNexus 从“功能越来越完整的分析 GUI”，推进到“会根据工作流上下文帮助用户提高结果可信度的分析工作台”。

这一阶段的关键词：

- 任务表达
- 上下文汇聚
- 受控建议
- 有界调参
- 多轮重试
- 结果回流
- 好用且美观

## 3. 产品边界

### 3.1 阶段 6 要做什么

- 让工作台更明确知道用户当前到底在做什么任务。
- 让 `Data -> Config -> Results -> Export` 从“页面顺序”变成“任务链路”。
- 让 `history / sample / batch / calibration / mask / joint / recent export` 开始围绕当前任务收敛成上下文。
- 让系统先给建议，再在严格边界内做有限参数尝试，而不是直接黑箱替用户决定。
- 让多轮尝试的理由、过程、候选结果都能回到现有界面上被看见。

### 3.2 阶段 6 明确不做什么

- 不做独立聊天式 Agent 主界面。
- 不做“自动写科研结论”的黑盒系统。
- 不做无边界自动修改所有参数的主动系统。
- 不在这一阶段重写底层分析引擎、数据库主结构或主窗口框架。
- 不把知识库问答、文献助手、审稿助手、远程协作平台一次性都混进来。

## 4. 阶段 6 的最小产品模型

阶段 6 的最小模型不是“先把 agent 做得很聪明”，而是先把这条链路做顺：

1. 工作台识别当前任务。
2. 工作台汇总当前任务最关键的上下文。
3. 系统给出下一步建议。
4. 对适合的场景，系统在边界内尝试少量参数变体。
5. 多轮尝试结果以候选方案的形式回流给用户。
6. 用户在现有工作台里继续看结果、比较结果、导出结果。

只要这条链是顺的，PolyNexus 就会开始明显像“懂工作流的分析工作台”，而不是一组分散功能。

## 5. 各任务最小闭环

### P6-T1. `workflow header` 任务卡片化

最小用户故事：

用户进入工作台后，不是只看到“当前技术 + 当前文件 + Ready/Running”，而是能一眼知道：

- 我现在在做哪类分析任务
- 当前任务走到哪一步了
- 下一步通常会落到哪个页面

这一版只做：

- 在现有 `workflow header` 内扩展为轻量任务卡片，不新建页面。
- 任务类型至少覆盖：
  - 单文件分析
  - sequence 分析
  - directory 批处理
  - joint analysis
  - sample / history 回溯恢复
- 任务卡片直接引用已有状态：
  - `technique`
  - `submodule`
  - `input_mode`
  - `source path`
  - `run state`

这一版不做：

- 独立任务中心
- 多任务并发调度器
- 自然语言任务解析器

验收标准：

- 用户一进来就更容易知道自己正在做什么任务。
- 切换 `single / sequence / directory / batch / joint` 时，任务表达会同步变化。
- 头部新增信息不会把现有界面挤乱，视觉上仍然干净。

### P6-T2. `Data / Config` 上下文建议栏

最小用户故事：

用户导入数据、切换 submodule、恢复历史记录后，工作台能在 `Data` 或 `Config` 页顶部告诉他：

- 现在最值得先检查什么
- 下一步最合适跳到哪里
- 哪些前置条件可能还没满足

这一版只做：

- 在现有 `Data / Config` 页增加轻量建议栏，不做独立面板体系。
- 建议主要来自现有状态：
  - `input_mode`
  - `submodule`
  - recent calibration
  - mask 状态
  - history 恢复来源
  - sample / batch 来源
- 建议只做三类动作：
  - 提醒
  - 跳转
  - 显示原因

这一版不做：

- 自动执行完整分析链
- 跨技术线复杂规划器
- 直接自动改配置

验收标准：

- 建议不是泛泛而谈，而是和当前上下文强相关。
- 用户能从建议直接跳到对应控件或页面。
- 建议即使错了，也不会把用户带到不可逆状态。

### P6-T3. `History / Sample / Joint` 上下文汇聚视图

最小用户故事：

用户不用自己在脑中拼装“最近一次校准在哪里、相关历史记录在哪里、样品 batch 在哪里、联合分析从哪里进入”，工作台会把和当前任务最相关的上下文收成一块。

这一版只做：

- 在现有工作台内做一个轻量“任务上下文”区域，优先挂在 `Config` 或 `Results` 邻近位置。
- 汇聚当前任务最相关的切片：
  - 最近 calibration
  - 最近相关 history run
  - 当前 sample / batch
  - 最近导出包
  - joint 关联入口
- 每个切片只支持：
  - 查看摘要
  - 一键跳转
  - 轻恢复

这一版不做：

- 全项目长期记忆系统
- embedding 检索
- 复杂知识图谱

验收标准：

- 用户找到相关上下文的路径明显变短。
- `history / sample / joint / calibration` 不再彼此割裂。
- 信息密度提升了，但界面仍然克制，不会像“信息墙”。

### P6-T4. `Results` 结果解读摘要

最小用户故事：

用户跑完后，除了结果表和图，还能先看到一段简洁、可靠、工程化的解读摘要：

- 这次到底完成了什么
- 结果是否存在明显风险
- 现在更应该信哪部分
- 下一步建议是补校准、调参数、看图还是回到数据入口

这一版只做：

- 在现有 `Results` 页增加结构化摘要区。
- 摘要优先复用已有数据：
  - result metrics
  - validation
  - mask 状态
  - history 对比信息
  - batch / joint 诊断
- 先走规则模板，不依赖大模型生成。

这一版不做：

- 自动写论文式结论
- discussion 自动生成
- 替用户判断研究假设是否成立

验收标准：

- 用户看完结果页后更容易知道“该看什么、暂时信什么、还差什么”。
- 摘要和现有参数表、日志、图表不冲突。
- 至少能把已有风险信号组织成更容易消化的结果提示。

### P6-T5. 受控多轮优化入口

最小用户故事：

当结果质量一般、上下文又足够完整时，用户可以让系统在严格范围内自动试几轮参数，再把候选配置和最好结果带回工作台。

这一版是阶段 6 的核心“agent 行为”，但必须收得很紧。

这一版只做：

- 基于现有 `AI tuning` 雏形，重构成更贴近主工作台的“受控优化”入口。
- 优化前先展示将使用的上下文：
  - 当前 technique / submodule
  - 当前数据来源
  - 当前 sample 推断
  - 当前默认参数或最近参数
  - 当前质量风险提示
- 多轮优化只允许在预定义参数边界里尝试。
- 每轮尝试都要留下：
  - 调了什么
  - 为什么调
  - 分数或质量如何变化
- 最终只输出：
  - 推荐配置
  - 备选配置
  - 不确定性说明
  - 一键应用并重跑

这一版不做：

- 任意参数空间自由搜索
- 跨 technique 联动自动规划
- 静默自动应用最佳结果
- 把优化结果直接包装成最终科研结论

验收标准：

- 用户能理解系统为什么开始调、调了什么、最好结果为什么更好。
- 调参是可取消、可查看、可拒绝的。
- 应用推荐配置后，仍然回到现有 `Config -> Run -> Results` 主流程。

### P6-T6. `Export` 任务化交付收口

最小用户故事：

用户导出时，导出的不只是“文件目录”，而是一个能说明本次任务上下文、结果可信度和建议查看顺序的交付包。

这一版只做：

- 在现有 `export bundle` 基础上补任务语义：
  - 当前任务类型
  - 当前 technique / submodule
  - 主要来源数据
  - 推荐先读哪个报告 / 图 / 表
  - 是否经过受控优化
  - 最终采用的是原始配置还是推荐配置
- README / manifest 更贴近一次完整分析交付，而不是只说明目录结构。

这一版不做：

- 自动打包外发平台
- 自动生成汇报 PPT
- 外部协同同步

验收标准：

- 用户隔几天再回来，也看得懂这次导出对应什么任务。
- 导出内容更像“分析交付包”，不是文件堆。
- 现有 `report / data / figures / metadata` 结构保持稳定。

### P6-T7. 阶段回归与边界固化

最小用户故事：

阶段 6 做完后，用户不会有“新功能更聪明了，但基础工作台反而不稳了”的感觉。

这一版只做：

- 给以下新增能力补最小回归保护：
  - 任务卡片
  - 建议栏
  - 上下文汇聚
  - 结果摘要
  - 受控多轮优化
  - 任务化导出
- 明确文案和行为边界：
  - 哪些只是建议
  - 哪些会真正执行
  - 哪些结果只是候选
- 对“专业工作台”与“全自动 agent”边界做一次产品收口。

这一版不做：

- 全量视觉重做
- 全量产品文档重写
- 大规模 E2E 平台建设

验收标准：

- 关键工作流不会因为新增 agent 行为而变得不可控。
- 新能力至少有定向测试。
- 阶段 6 的产品边界清晰、稳定、可复述。

## 6. 推荐顺序

阶段 6 推荐执行顺序调整为：

1. `P6-T1 workflow header 任务卡片化`
2. `P6-T2 Data / Config 上下文建议栏`
3. `P6-T3 History / Sample / Joint 上下文汇聚视图`
4. `P6-T4 Results 结果解读摘要`
5. `P6-T5 受控多轮优化入口`
6. `P6-T6 Export 任务化交付收口`
7. `P6-T7 阶段回归与边界固化`

原因：

- T1 先把“当前在做什么任务”说清楚，这是整个阶段的锚点。
- T2 先把“下一步建议”长进现有工作流，而不是先做复杂自动化。
- T3 把建议背后的上下文收起来，否则建议会显得悬空。
- T4 让结果页开始承担“解释和风险提示”，形成闭环。
- T5 再把已有 AI tuning 收编成真正受控、可解释的 agent 行为。
- T6 最后让导出也继承任务语义，形成完整交付收口。
- T7 压后做回归和边界固化，防止系统一路长偏。

## 7. 下一步入口

下一步直接进入 `P6-T1 workflow header 任务卡片化`，第一刀继续保持足够小：

1. 不新建页面，只改现有 `workflow header`。
2. 只读取当前已存在的上下文，不引入新存储。
3. 先把任务类型、任务阶段、下一步目标页表达清楚。
4. 先把信息表达做对、做顺、做好看，再做后续建议和优化。

## 8. 视觉与交互要求

阶段 6 虽然主打的是“上下文 + agent 行为”，但必须同时满足两个要求：

- 足够好用
- 足够美观

这一阶段的 UI 原则：

- 不新增漂浮的大型二级面板。
- 优先利用现有 header、tab 页内部、group box 和摘要区。
- 信息层级清楚，第一眼只看任务与风险，第二眼再看细节。
- 建议、摘要、优化入口都要像工作台原生能力，而不是外挂工具。
- 颜色、间距、密度保持克制，不把科学工作台做成花哨“AI 产品页”。

## 9. 阶段回归底线

阶段 6 每完成一个任务，至少回归这些场景：

1. GUI 能正常启动，切换 technique / submodule 不报错。
2. 单文件、sequence、directory、batch、joint、sample 回溯都还能正常进入。
3. 导入、校准、mask、history、results、export 原有闭环不回归。
4. 建议型入口只做建议，不静默执行高风险动作。
5. 受控优化必须可取消、可拒绝、可回退。
6. 新增任务表达、结果摘要、优化入口至少有定向测试。

## 10. 阶段完成定义

满足下面条件即可视为阶段 6 完成：

- 工作台能明确表达“当前任务”而不是只展示控件状态。
- 系统能基于已有上下文给出可信的下一步建议。
- `history / sample / joint / calibration / export` 开始以任务上下文形式被重新组织。
- 结果页能更自然地表达“完成了什么、风险在哪里、下一步是什么”。
- 受控多轮优化能在既有工作流中运行，并把候选配置与理由回流到工作台。
- 导出结果更像完整任务交付包，而不是纯文件集合。
- 整体依然保持“专业分析工作台优先，agent 行为渐进增强”的边界。
