# PolyNexus 阶段 7 任务清单

## 0. 当前定位

阶段 7 不再解决“有没有 agent 行为”这个问题，因为阶段 6 已经给出了清晰答案：

**PolyNexus 应继续沿着“带 agent 行为的专业分析工作台”演化。**

所以阶段 7 的重点不是再加一批零散 AI 入口，而是把阶段 6 已经出现的这些能力继续收成更完整的任务回路：

- 任务识别
- 上下文组织
- 受控优化
- 结果回流
- 历史对比
- 导出交付

阶段 7 要做的是：

**让这些局部 agent 行为开始形成更稳定的“审阅 - 比较 - 再尝试 - 确认”闭环。**

## 0.1 当前收口状态

截至目前，阶段 7 的 P7-T1 到 P7-T5 已经完成，并且完成了对应的定向回归验证。

- P7-T1 候选结果比较面板：已完成
- P7-T2 结果确认与标记：已完成
- P7-T3 受控优化二次回路：已完成
- P7-T4 审阅式导出：已完成
- P7-T5 阶段回归与边界固化：已完成

已验证的主链路包括：

- results compare 候选切换与当前结果保护
- 结果确认 / 取消确认
- AI tune 二次上下文传递
- work memory 当前确认状态
- 审阅式导出包
- 阶段 7 边界回归扫描

## 1. 阶段目标

阶段 7 只解决一个问题：

把 PolyNexus 从“已经会提示、会受控优化、会回流结果的分析工作台”，推进到“能帮助用户完成多轮审阅和结果确认的可信分析工作台”。

这一阶段的关键词：

- 审阅闭环
- 多轮比较
- 候选结果管理
- 可信确认
- 任务回路稳定化

## 2. 阶段边界

### 2.1 阶段 7 要做什么

- 让受控优化的候选结果不只是一份报告，而是能进入更清楚的“比较与确认”流程
- 让用户更容易比较：
  - 原始结果
  - 推荐参数重跑结果
  - 历史最优结果
  - 同一 batch / sample 下的相邻候选
- 让系统能把“这次为什么值得信 / 为什么还不能完全信”表达得更稳
- 让导出交付从“任务化”进一步走向“可审阅、可复盘、可确认”

### 2.2 阶段 7 明确不做什么

- 不做全自动科研结论生成
- 不做开放式聊天主界面重构
- 不做无边界 agent 自主规划器
- 不在这一阶段重写底层分析引擎、数据库主结构或主窗口框架
- 不把文献问答、知识库、远程协作平台一次性混进来

## 3. 阶段 7 的最小产品模型

阶段 7 的最小模型不是“让 agent 更像人”，而是先把这条链路做稳：

1. 用户得到一个结果
2. 工作台明确告诉他这个结果来自哪里
3. 用户能方便地把它和基线 / 历史 / 邻近候选进行比较
4. 系统能提示“下一步是接受、再试一轮，还是回到数据/配置”
5. 用户能把最终确认的结果作为一个更可信的交付包带走

只要这条链顺了，PolyNexus 的 agent 行为就会明显更像“审阅助手”，而不是一堆分散建议。

## 4. 各任务最小闭环

### P7-T1. 候选结果比较面板

最小用户故事：

用户完成一次受控优化后，不只看到一份多轮报告，还能在主工作台中快速比较：

- 当前结果
- 推荐参数重跑结果
- 历史上一个同技术线结果
- 同 batch 下最邻近的可比 run

这一版只做：

- 在现有 `Results` / `History` 邻近区域增加轻量候选比较入口
- 复用现有 history compare 能力和结果摘要能力
- 优先比较：
  - 关键指标
  - 风险摘要
  - 结果来源
  - 关键参数变化

这一版不做：

- 完整 diff 工作台
- 大型可视化比较中心
- 跨多个 technique 的复杂候选矩阵

验收标准：

- 用户能比现在更快看出“推荐结果到底比原始结果好在哪”
- 比较入口仍然留在现有工作台，不变成额外系统

### P7-T2. 结果确认与标记

最小用户故事：

用户在多轮尝试后，能明确把某个结果标成“当前确认结果”，而不是只能靠记忆或导出目录判断。

这一版只做：

- 给当前 run 增加轻量“确认结果”标记
- 让 history / export / work memory 能识别这个状态
- 只支持单用户、本地工作台内使用

这一版不做：

- 复杂审批流
- 多人签署
- 远程同步确认状态

验收标准：

- 用户能明确知道“当前哪一个结果是暂时确认的”
- 确认状态不会破坏原始运行记录

### P7-T3. 受控优化二次回路

最小用户故事：

当推荐参数重跑结果仍然不够理想时，用户可以在已有上下文基础上再来一轮，但系统会更明确告诉他：

- 上一轮为什么被接受
- 这次再试的目标是什么
- 还剩哪些高风险点没有解决

这一版只做：

- 在 `Controlled Optimization` 再次启动前补“上一轮结果摘要”
- 把上一轮 stop reason / rollback reason / 当前风险提示前置到确认上下文里
- 保持当前受控边界，不扩大参数空间

这一版不做：

- 自动无限多轮优化
- 跨技术线联合优化
- 主动跳过用户确认

验收标准：

- 用户能理解“为什么要再试一轮”
- 第二轮启动前的信息更完整，而不是重新从零开始

### P7-T4. 审阅式导出

最小用户故事：

导出包不仅说明“本次任务是什么”，还更像一个可审阅包，能让未来的自己或同事快速回答：

- 最终确认的是哪个结果
- 还有哪些风险未关闭
- 建议优先看哪些对比图和摘要

这一版只做：

- 在 manifest / README 中补：
  - 是否为 confirmed result
  - 与基线相比的关键改善摘要
  - 当前仍保留的风险提示
- 保持现有目录结构不变

这一版不做：

- 自动出 PPT
- 自动写论文结论
- 自动远程分享审阅链接

验收标准：

- 导出包更像“可审阅交付”而不是单纯目录
- 未来复盘时更容易恢复当时的判断过程

### P7-T5. 阶段回归与边界固化

最小用户故事：

阶段 7 做完后，用户会感觉工作台更会帮自己“确认结果”，但不会觉得系统开始越权替自己做决定。

这一版只做：

- 为结果比较、确认标记、二次受控优化、审阅式导出补最小定向回归
- 再次固化产品边界：
  - agent 负责建议、比较、组织和提醒
  - 最终科研判断仍由用户完成

这一版不做：

- 大规模全链路 E2E 平台
- 全量 UI 重做
- 无边界自动推理系统

验收标准：

- 关键主链路保持稳定
- 新能力不制造“系统替我拍板”的错觉

## 5. 推荐顺序

阶段 7 推荐执行顺序：

1. `P7-T1 候选结果比较面板`
2. `P7-T2 结果确认与标记`
3. `P7-T3 受控优化二次回路`
4. `P7-T4 审阅式导出`
5. `P7-T5 阶段回归与边界固化`

原因：

- T1 先把“怎么看差异”做出来，这是整个阶段的锚点
- T2 再把“最终认哪个结果”说清楚
- T3 才有意义把第二轮受控优化和上一轮结果真正串起来
- T4 最后把确认后的交付包收口
- T5 压后做阶段固化，避免一路长偏

## 6. 阶段回归底线

阶段 7 每完成一个任务，至少检查：

1. GUI 正常启动，主分析流程不报错
2. single / sequence / directory / batch / joint / history restore 主链路不回归
3. 受控优化仍然可取消、可拒绝、可回退
4. 结果比较不会篡改原始结果
5. 结果确认不会覆盖历史运行记录
6. 导出包结构仍保持 `report / figures / data / metadata`

## 7. 阶段完成定义

满足下面条件即可视为阶段 7 完成：

- 用户能更容易比较推荐结果、原始结果和历史结果
- 用户能更明确地确认“当前可信结果”
- 二次受控优化能承接上一轮上下文，而不是重新开始
- 导出包开始具备更清楚的审阅语义
- 产品仍然保持“专业工作台优先，agent 行为渐进增强”的边界
